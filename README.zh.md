# dsh-humanize

[English](README.md) | 简体中文 | [技术细节](DESIGN.md)

> 让推理模型专注干活，让交付内容好好说人话。

`dsh-humanize` 是一个面向 `deepseek-harness` 的插件，旨在解决编码特化模型在复杂任务中输出机器化黑话的问题。

## 为什么需要它

编码特化模型能处理复杂工程推理，但输出的文字偏向机器化黑话。人类阅读这类文字要多花一份心思。

在主提示词里堆叠大量风格与修辞约束，会分散模型的推理注意力。复杂任务的效率随之下降。

## 核心构想

`dsh-humanize` 的核心理念是**将逻辑推理与文风润色解耦**：

- **按标记区分**：在内容写入时，先区分纯代码或数据与面向人类阅读的内容。只有面向人类阅读的内容会触发写入审查。
- **风格约定**：引入 `PROSE.md`，作为统一行文表达的标准。
- **逐条溯源**：审查过程对照 `PROSE.md` 中的规范分点进行批注，定位表达不当之处。
- **延迟应用**：审查在后台进行，主会话照常往下走，批注按需应用，压缩结束后也会自动润色。

## 安装

从 GitHub 安装：

```sh
dsh plugin --profile web add github:Lry722/dsh-humanize
```

本地开发时用 link 方式装载当前目录：

```sh
dsh plugin --profile web add link:/path/to/dsh-humanize
```

安装完成后重启 dsh 才会生效。

## 命令速查

| 命令 | 作用 |
| --- | --- |
| `/humanize [路径]` | 按暂存批注润色一次，然后复审刚改过的文件。 |
| `/humanize-loop [路径]` | 循环执行行文润色与复审，直到没有批注或达到轮次上限。 |
| `/humanize-review [路径]` | 审查路径下受 git 管理的文件。 |
| `/humanize-review --changed [路径]` | 只审查相对 HEAD 有改动的文件。 |
| `/humanize-review --recent N [路径]` | 审查最近 N 个提交涉及的文件。 |

路径默认为会话工作目录。`--changed` 和 `--recent` 可以写在路径前面或后面。审查只保留命中至少一份规范的文件。

## 配置

在设置页的插件列表中找到 dsh-humanize，打开那一行的配置。所有设置改完之后立即生效。

### 设置项

| 设置 | 默认值 | 说明 |
| --- | --- | --- |
| `reviewProvider`、`reviewModel` | 会话模型 | 审查调用的提供方和模型，从宿主模型目录里选择。 |
| `reviewReasoningEffort` | 模型默认值 | 审查调用的推理等级，从所选模型公布的等级里选择。 |
| `mergeProvider`、`mergeModel` | 会话模型 | 润色子代理的提供方和模型，使用与审查相同的控件，适用于所有润色触发方式。 |
| `mergeReasoningEffort` | 会话推理等级 | 润色子代理的推理等级，从所选模型公布的等级里选择。 |
| `reviewConcurrency` | `3` | 审查调用的并发上限，最小值为 1。 |
| `reviewRetries` | `1` | 审查失败后的重试次数，取值范围为 0 到 3。 |
| `reviewIntervalSeconds` | `60` | 下一次写入审查距上一次审查结束的最小间隔，取值范围为 0 到 3600。设为 0 时立即审查。 |
| `loopMaxRounds` | `3` | `/humanize-loop` 的轮次上限，取值范围为 1 到 10。 |
| `saveTurnOutputs` | `false` | 把主会话最新一轮回复保存到系统临时目录。 |
| `mergeOnCompaction` | `true` | 上下文压缩结束时按暂存批注自动润色。 |
| `storageDir` | 留空 | 暂存批注的保存位置。默认位置为 `~/.dsh/humanize`。 |

审查模型和润色子代理的模型下面各有一个测试按钮。点击后会发一条最小请求，确认提供方、模型和推理等级能正常返回。测试前需要把一对模型字段都填好。实际调用时，一对字段只填一项，整对跟随会话模型。

### 存储位置

设置页底部展示暂存批注、批注历史、审查请求记录和最终回复输出的实际保存位置。每条路径旁边都有复制按钮。

相对路径按进程工作目录解析。改动 `storageDir` 后，旧目录里的内容留在原处。

### 配置文件

也可以在 profile 的 `cordis.patch.yml` 里为 `dsh-humanize` 条目传入同样的配置：

```yaml
- id: dsh-humanize
  config:
    settings:
      reviewProvider: deepseek
      reviewModel: deepseek-chat
```

## 编写规范

### 来源与范围

规范有三种来源：

- 用户全局规范放在 `~/.dsh/PROSE.md`，作用于所有目标文件。
- 项目规范放在项目根目录的 `.agents/prose/*.md`。只读取这个目录下的直接子文件。
- 目录规范放在被审查文件的目录或上级目录，文件名为 `PROSE.md`。

项目根目录按目标文件所在的 git 仓库确定。会话从仓库子目录启动时，仍会读取仓库根的 `.agents/prose/`。项目根目录的旧版 `PROSE.md` 继续作为目录规范生效。

`base.md` 是普通的项目规范。文件名不决定作用范围或优先级。省略 include 时，它作用于整个项目。显式写 `include: ["**/*"]` 效果相同。

每份规范都有隐式范围：用户规范作用于所有目标文件，项目规范作用于整个项目，目录规范作用于所在子树。省略 include 时，规范作用于整个隐式范围。

### include 模式

显式 include 用 .gitignore 语法收窄当前规范的范围，只对这份规范生效。空的 include 列表不匹配任何文件。一份规范的模式不会影响另一份规范。

例如，一份项目规范可以覆盖多个目录和根目录的更新日志：

```markdown
---
include:
  - "docs/"
  - "examples/"
  - "/CHANGELOG.md"
---
```

含斜杠的模式按规范的匹配基准锚定。项目规范以项目根目录为基准，目录规范以所在目录为基准。`/CHANGELOG.md` 只命中项目根目录下的文件。

同一组 include 里，最后一次命中的模式生效。`!` 前缀表示排除。

### 优先级与继承

priority 缺省为 0，数值小的先合并。数值相同时，依次排列用户规范、项目规范、目录规范。项目规范按文件路径排序，目录规范从浅到深排列。冲突时，后出现的规则优先。

`inherit: false` 只在这份规范命中时生效。解析到它时，清空此前已经接收的规范，再接收当前规范。排序更靠后的规范继续合并。

### 规则格式

每份适用规范必须包含一级标题 `# Rules`。这个章节里的编号行是审查规则。其他一级标题下的内容原样交给审查和润色，作为术语解释或补充说明。例如：

```markdown
# Rules

1. 平铺直叙。
2. 严禁滥用括号。

# Explanation

滥用：xxx
```

只有 `# Rules` 章节里的编号行参与全局规则编号，其他章节里的编号保持原样。缺少 `# Rules` 的适用规范会让审查报错。

## 审查流程

### 进入审查的条件

文件是否进入审查由适用规范决定。至少命中一份规范，并且合并后的规则里至少有一条编号规则时，文件才会进入审查。include 负责选出适用规范，priority 和 inherit 只影响规则合并，不单独声明审查范围。

批次收集先按规范是否命中过滤文件。命中但没有编号规则的结果留给审查管线统计。写入审查、批次审查和润色后的复审共用这个判断。

图片、压缩包、字体和编译产物这类二进制文件跳过审查。判断取文件开头的样本，写入审查和批次审查都适用。批次审查的完成说明会报告跳过的数量。

模型通过包装后的 `write` 或 `edit` 工具写文件时，必须声明 `human_facing`。面向人类阅读的内容传入 true，纯代码或数据传入 false。标记为 true 的写入会进入审查，其余写入跳过。经其他工具写入，例如 shell 命令，不受这项检查约束。程序化调用缺少这个字段时按 false 处理，并记一条警告。

### 审查时机

每次审查结束后，下一次写入审查默认等待一分钟再开始。间隔内到达的写入合并到下一次审查。

已有文件的写入审查只看本次改动的区段。新建文件按全文审查。审查调用仍然发送完整文件，标记只限定新批注的位置。

同一文件的审查串行执行。不同会话或子代理的写入各自排队，待办按 agent 分开，各自保留自己的队列。润色运行期间，发起润色的 agent 的审查让路。其他 agent 在这些目标文件上的审查同样让路。批次审查和润色复审跳过这个间隔，立即执行。

### 并发与重试

所有审查调用共用 `reviewConcurrency`。批次实际并发还受待审文件数限制。并发过高时可能触发模型提供方的速率限制。

触发速率限制的调用和审查超时都会记为失败并重试。每重试一次，等待时间都比上一次长。重试次数用完后仍然失败，就记为最终失败。写入审查和批次审查共用这套重试。

批次审查结束时，会列出仍然失败的文件和原因，最多三条，其余只统计条数。写入审查连续失败时，任务列表会出现一条失败记录，提示检查审查模型的配置。

### 审查请求记录

审查请求记录另存到系统临时目录，具体位置显示在设置页底部。审查结果解析失败时，模型的原始响应也写在审查请求记录旁边，便于排查时对照。

## 最终回复输出

### 保存

`saveTurnOutputs` 默认关闭。开启后，主会话每一轮结束时，插件取这一轮最后一条含可见正文的助手消息，写入系统临时目录下的 `dsh-humanize-<uid>/output/<会话标题>--<短ID>.md`。每次覆盖上一版，只保留最新回复。

推理内容、工具调用、空消息和子代理的内部回复都不写入。项目目录里不会创建输出文件。

### 输出文件与清理

文件名使用首次保存时的会话标题。路径分隔符等文件系统不安全字符会替换为下划线，空标题使用 `untitled-session`。短 ID 后缀避免同名会话互相覆盖。会话改名后继续沿用首次使用的文件，插件重载后也能按后缀找回。

保存新输出时，超过 24 小时未更新的临时输出会被清理。清理扫描最多每小时执行一次。

规范按当前工作目录下的逻辑路径 `.agents/output/<会话标题>--<短ID>.md` 发现和匹配。这个路径只用于规则计算，不要求文件存在。审查和润色共用同一个逻辑路径，文件读写始终使用临时目录里的真实路径。

新版首次保存后，会移除这个会话旧版留在项目内的输出及其暂存批注。

### 润色

每次写入只保存原始输出，并清除上一轮批注。审查只在用户点击润色图标后开始。最新有效的那一轮回复会在助手操作栏显示润色图标。点击图标后，插件立即全量审查最新回复，不等待 `reviewIntervalSeconds`。没有适用规则或审查没有产出批注时，润色流程就此结束，只更新输出状态。

审查产生批注时，插件静默执行一轮行文润色。行文润色完成后立即结束输出润色，不再复审。这轮行文润色不创建任务行，也不向主会话发送结果通知。

手动 `/humanize` 和 `/humanize-loop` 的进度、结果与复审保持不变。同一会话的保存、审查与行文润色串行执行，不同会话的输出润色也依次派发。

### 操作栏

保存后，最新有效的那一轮回复的助手操作栏在 Fork 按钮右侧显示润色图标。点击后显示润色中的加载图标。

处理结束后比较最终文件与本轮原始正文。内容实际变化时显示可点击的查看图标，点击图标后在右侧栏用内置 Markdown 预览打开输出。

无变化或失败时只显示对应状态图标，鼠标悬停在图标上时可以查看状态说明。原始助手回复保持原样，右侧栏只在用户点击查看图标时打开。

更早的轮次没有入口，避免打开已被后续轮次覆盖的新内容。

## 批注暂存

### 暂存文件

批注的默认保存位置是 `~/.dsh/humanize/annotations/`，可以在设置页修改。保存位置与被审查文件的路径一一对应。批注可以直接编辑。

暂存文件按完整规则条文分组，规则标题只写条文。全局编号只用于校验当次审查输出，不写入暂存文件。暂存内容不写文件名。复审时按规则条文匹配。

### 历史

覆盖或删除暂存文件前，插件把当时的暂存原文追加到历史目录。历史目录 `history/` 和审查请求记录同在系统临时目录下，具体路径显示在设置页。历史目录按被审查文件的路径组织。

每次操作都会新增一个文件，保留旧快照。文件名包含归档时间和操作类型。审查清空、润色清空和孤儿清理使用不同标记。

历史只在排查时查阅。插件会一直保留历史文件，临时目录的清理交给系统策略。

## 行文润色

### 命令与范围

输入 `/humanize 路径`，按指定文件或目录的暂存批注润色行文。省略路径时使用当前工作目录。路径是文件时只润色这个文件，是目录时润色目录下所有带暂存批注的文件。

输入 `/humanize-loop 路径` 循环执行行文润色与复审。每轮润色完成后，对刚润色过的文件逐个复审。复审产生的新批注进入下一轮润色。复审没有新批注或达到轮次上限时，循环结束。

手动润色完成后，主会话会收到一份结果说明。自动润色不注入这项通知。

### 润色子代理

行文润色在单独的上下文里进行。每个父会话复用一个润色子代理。续用前，上一轮对模型可见的润色请求、回复和工具调用会被一条固定的历史重置占位消息替换，不再重复发给模型。原始会话日志仍然保留。

润色子代理的模型跟随润色设置。子代理只带文件读写、检索和 persona 工具。它的写入跳过审查。

### 润色过程与复审

行文润色一开始，先中止正在运行的审查。排队中的审查直接丢弃，已经产出的批注也一并丢弃。其他会话在这些文件上的审查同样让路。

润色成功后，暂存文件中对应的批注清空。润色失败时保留批注。

手动润色成功后，插件对刚改过的文件再跑一次审查，这次审查叫复审。复审产生的新批注同样留在暂存文件中。润色结果写在主会话的结果说明里，复审结果写在任务行里。

`/humanize` 和 `/humanize-loop` 复审失败时，任务以失败结束，不再判定为收敛，并在主会话补一条说明。

同一时间只允许一条润色运行，跨会话也一样。派发前，插件检查同一会话里有没有还活着的润色子代理，有就拒绝新的派发。

润色或复审期间遇到插件重载，这次运行到此结束。已经完成的润色照常清空暂存批注。未完成的润色保留暂存批注。手动润色可以重新执行命令继续。

### 循环润色

润色目标、轮次和待复审文件留在内存里。中途暂存的批注为空时，等复审跑完再判断是否还有新批注。

### 自动润色

`mergeOnCompaction` 默认开启。上下文压缩结束时，插件按会话工作目录下的全部暂存批注润色行文。关闭后压缩不再触发润色，手动命令与输出润色不受影响。这类润色静默执行，跳过任务行和结果通知。它们仍会复审刚改过的文件。

输出润色触发的行文润色同样静默执行。它只跑一轮，不复审。具体流程见“最终回复输出”一节。

### 后台任务

只有手动 `/humanize` 和 `/humanize-loop` 会登记润色任务。循环润色的进度条显示当前轮次和本轮批注数。压缩触发的润色和输出润色触发的行文润色在后台静默执行，不创建任务行，也不注入结果通知。

`/humanize` 和 `/humanize-loop` 的任务可以在任务列表里取消。循环润色的取消在下一轮开始前生效。已经完成的润色照常清空暂存批注。

在 profile 里配置了 hmr 监听本插件目录时，改动本插件自己的源码会触发插件重载。重载会结束正在进行的润色运行。手动润色可以重新执行命令继续。

## 批次审查

### 三种模式

输入 `/humanize-review 路径`，派发一次批次审查。路径默认为当前工作目录。标志可以写在路径前面或后面。

| 模式 | 检查的文件 | 审查范围 |
| --- | --- | --- |
| 默认 | 路径下受 git 管理的文件。 | 全文。 |
| `--changed` | 相对 HEAD 有改动的文件，加上未被 git 忽略的新文件。 | 改动区段。新文件按全文审查。 |
| `--recent N` | 最近 N 个提交涉及、且仍在工作区的文件。 | 当前工作区全文。 |

`--changed` 和 `--recent` 会跳过删除的文件。默认模式按受 git 管理的路径收集文件，缺失的受跟踪文件可能记为读取失败。`--recent` 和 `--changed` 不能同时使用。

### 选择细节

`--changed` 的改动文件包括工作区改动、已暂存但尚未提交的改动，以及未被 git 忽略的新文件。审查仍发送完整文件，只把批注范围圈到改动区段。没有改动文件时，任务以完成结束，并提示没有需要审查的改动。

`--recent N` 只用提交确定文件范围。审查使用当前工作区内容，覆盖全文。提交数少于 N 个时退化为 HEAD 里的全部文件。工作区不存在的文件跳过。

### 运行与终态

审查在后台进行，显示为一个后台任务。进度条在输入框上方更新。会话头部的任务列表同样显示该任务。审查在单独的上下文里进行，读到的内容与会话本身分开。

目标需要是 git 仓库，并且仓库状态能正常读取。任一条件缺失时，任务以失败结束并给出原因。目标里没有可审查的文件时，任务以完成结束，并提示没有可审查的文件。

三种模式都只保留命中至少一份规范的文件，审查管线再要求至少有一条编号规则。二进制文件跳过审查，完成说明会报告跳过的数量。

批次审查共用审查并发和重试规则。失败清单见“并发与重试”一节。

## 提示词

发给模型的提示词都放在包的根目录 `prompts/` 下，直接编辑即可：

- `prompts/review-system.md`：所有审查调用的 system 提示词。
- `prompts/merge-request.md`：派发润色子代理时发给它的用户消息，包含润色请求文件的路径。
- `prompts/merge-header.md`：每条润色消息开头的提示词。
- `prompts/human-facing-field.md`：包装工具里 `human_facing` 字段的描述。

审查和润色每次调用都会重新读取对应的提示词文件。`human_facing` 字段的说明在注册包装工具时读取，改完后对新会话生效。
