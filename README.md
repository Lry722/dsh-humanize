# dsh-humanize

> 让推理模型专注干活，让交付内容好好说人话。

`dsh-humanize` 是一个面向 `deepseek-harness` 的插件，旨在解决编码特化模型在复杂任务中输出机器化黑话的问题。

---

## 为什么需要它？

编码特化模型能处理复杂工程推理，但输出的文字偏向机器化黑话。人类阅读这类文字要多花一份心思。

在主提示词里堆叠大量风格与修辞约束，会分散模型的推理注意力。复杂任务的效率随之下降。

---

## 核心构想

`dsh-humanize` 的核心理念是**将逻辑推理与文风润色解耦**：

- **标记旁路**：在内容写入时，区分纯代码或数据与面向人类阅读的内容，仅对面向人类阅读的内容触发写入审查。
- **风格契约**：引入 `PROSE.md`，一份类似 `AGENTS.md` 的层级规范文档，支持多级目录规则叠加，作为统一行文表达的标准。
- **逐条溯源**：审查过程对照 `PROSE.md` 中的规范分点进行批注，定位表达不当之处。
- **延迟应用**：审查在旁路进行，主任务流照常推进，批注等用户需要时再合并。

---

## 安装

```sh
dsh plugin --profile web add link:/path/to/dsh-humanize
```

安装完成后重启 dsh 才会生效。

## 配置

在设置页的插件列表中找到 dsh-humanize，打开那一行的配置。设置页底部展示实际使用的保存位置，位置旁边有复制按钮。下面七个参数改完即生效：

- `reviewProvider` 与 `reviewModel`：审查用的模型，从宿主模型目录里下拉选择。默认跟随会话当前使用的模型。
- `reviewReasoningEffort`：审查模型的推理等级，从所选模型公布的等级里下拉选择。默认采用模型自身的默认值。
- `reviewConcurrency`：并发审查数，最小值为 1，默认值为 3。
- `reviewRetries`：失败重试次数，最小值为 0，最大值为 3，默认值为 1。
- `loopMaxRounds`：循环合并的轮次上限，最小值为 1，最大值为 10，默认值为 3。
- `mergeOnCompaction`：上下文压缩结束时是否自动合并整个项目的暂存批注，默认 true。设为 false 后，只在手动执行 `/humanize` 时合并。
- `storageDir`：暂存批注和审查请求留档的保存位置，留空使用默认位置 `~/.dsh/humanize`。改动后旧目录里的内容留在原处。

并发审查数最多等于待审文件的数量。并发过高时可能触发模型提供方的速率限制。

触发速率限制的调用记为失败并重试。审查调用超时会被中止，中止同样记为失败并重试。每重试一次，间隔就比上一次长一点，超过重试次数记为失败。写入审查和批次审查共用这套重试。

批次审查结束后，会列出仍然失败的文件和原因。写入审查连续失败时，任务列表会出现一条失败记录，提示检查审查模型的配置。

也可以在 profile 的 `cordis.patch.yml` 里为 `dsh-humanize` 条目传入同样的配置：

```yaml
- id: dsh-humanize
  config:
    settings:
      reviewProvider: deepseek
      reviewModel: deepseek-chat
```

## 使用

在被审查文件的目录或上级目录放 `PROSE.md` 规范，用户全局规范放在 `~/.dsh/PROSE.md`。范围越小的规则优先级越高。

PROSE.md 的文件头可以用 include 声明规范作用的文件范围，语法参考 .gitignore：

```markdown
---
include:
  - '*.md'
  - 'docs/**/*.txt'
  - '!drafts/'
---
```

声明过 include 后，命中模式的文件才进入审查。写入审查和批次审查都按这个范围执行。声明 include 之前，规范作用于所有文件。

模型写文件时必须声明 `human_facing`：面向人类阅读的内容传 true，纯代码或数据传 false。标记为 true 的写入会进入审查，其余写入跳过。审查只看本次改动的区段。

批注暂存在 `~/.dsh/humanize/annotations/` 下，存放路径与被审查文件的路径一一对应，支持直接编辑。保存位置可以在设置页修改。

输入 `/humanize 路径` 合并指定文件或目录的批注。省略路径时使用当前工作目录。

合并在单独的上下文里进行，主会话的上下文保持原样。合并完成后主会话收到一行结果说明，对应批注随之清空。

合并一开始，进行中的批次审查会被中止，在途和排队的审查随之丢弃，结果一并过期。

输入 `/humanize-loop 路径`，循环执行合并与复审。每轮合并后对被合并的文件逐个复审，复审产生的新批注进入下一轮合并，直到复审没有新批注或达到轮次上限。

循环显示为一个后台任务，进度条给出当前轮次和本轮批注数。

可以在任务列表里取消，取消在下一轮开始前生效。

输入 `/humanize-review 路径`，主动派发一次批次审查。审查范围先限定在受 git 管理的文件，再按 include 模式过滤。

审查在后台进行，显示为一个后台任务。进度条在输入框上方更新。会话头部的任务列表同样显示该任务。审查在单独的上下文里进行，读到的内容与会话本身分开。

目标目录需要是 git 仓库，并且仓库状态能正常读取。任一条件缺失时，任务以失败结束并给出原因。

## 提示词

发给模型的提示词都放在包的根目录 `prompts/` 下，直接编辑即可：

- `prompts/review-system.md`：写入审查调用的 system 提示词。
- `prompts/merge-header.md`：`/humanize` 合并消息开头的提示词。
- `prompts/human-facing-field.md`：包装工具里 `human_facing` 参数的描述。

每次审查或合并都会重新读取对应文件，改完保存即生效。
