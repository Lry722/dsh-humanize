# dsh-humanize

> 让推理模型专注干活，让交付内容好好说人话。

`dsh-humanize` 是一个面向 `deepseek-harness` 的插件，旨在解决编码特化模型在复杂任务中输出机器化黑话的问题。

---

## 为什么需要它？

编码特化模型能处理复杂工程推理，但输出的文字偏向机器化黑话。人类阅读这类文字要多花一份心思。

在主提示词里堆叠大量风格与修辞约束，会分散模型的推理注意力。复杂任务的效率随之下降。

---

## 核心构想

`dsh-humanize` 的核心理念是**将逻辑推理与文风润色解耦**：

- **按标记区分**：在内容写入时，先区分纯代码或数据与面向人类阅读的内容。只有面向人类阅读的内容会触发写入审查。
- **风格约定**：引入 `PROSE.md`，作为统一行文表达的标准。这是一份类似 `AGENTS.md` 的层级规范文档，支持多级目录规则叠加。
- **逐条溯源**：审查过程对照 `PROSE.md` 中的规范分点进行批注，定位表达不当之处。
- **延迟应用**：审查在后台进行，主会话照常往下走，批注等用户需要时再合并。

---

## 安装

```sh
dsh plugin --profile web add link:/path/to/dsh-humanize
```

安装完成后重启 dsh 才会生效。

## 配置

在设置页的插件列表中找到 dsh-humanize，打开那一行的配置。设置页底部展示实际使用的保存位置，位置旁边有复制按钮。下面这些参数改完之后立即生效：

- `reviewProvider` 与 `reviewModel`：审查用的模型，从宿主模型目录里下拉选择。默认跟随会话当前使用的模型。
- `reviewReasoningEffort`：审查模型的推理等级，从所选模型公布的等级里下拉选择。默认采用模型自身的默认值。
- `reviewConcurrency`：并发审查数，最小值为 1，默认值为 3。
- `reviewRetries`：失败重试次数，最小值为 0，最大值为 3，默认值为 1。
- `loopMaxRounds`：循环合并的轮次上限，最小值为 1，最大值为 10，默认值为 3。
- `mergeOnCompaction`：上下文压缩结束时是否自动合并整个项目的暂存批注，默认 true。设为 false 后，只在手动执行 `/humanize` 或 `/humanize-loop` 时合并。
- `storageDir`：暂存批注和审查请求记录的保存位置，留空使用默认位置 `~/.dsh/humanize`。改动后旧目录里的内容留在原处。

并发审查数最多等于待审文件的数量。并发过高时可能触发模型提供方的速率限制。

触发速率限制的调用记为失败并重试。审查调用超时会被中止，中止同样记为失败并重试。每重试一次，间隔就比上一次长一点，超过重试次数记为失败。写入审查和批次审查共用这套重试。

批次审查结束后，会列出仍然失败的文件和原因。写入审查连续失败时，任务列表会出现一条失败记录，提示检查审查模型的配置。

也可以在 profile 的 `cordis.patch.yml` 里为 `dsh-humanize` 条目传入同样的配置：

```yaml
- id: dsh-humanize
  config:
    settings:
      reviewProvider: deepseek
      reviewModel: deepseek-chat
```

## 使用

在被审查文件的目录或上级目录放 `PROSE.md` 规范，用户全局规范放在 `~/.dsh/PROSE.md`。范围越小的规则优先级越高。

PROSE.md 的文件头可以用 include 声明规范作用的文件范围，语法参考 .gitignore：

```markdown
---
include:
  - '*.md'
  - 'docs/**/*.txt'
  - '!drafts/'
---
```

声明过 include 后，命中模式的文件才进入审查。写入审查和批次审查都按这个范围执行。没有声明 include 时，规范作用于所有文件。

模型写文件时必须声明 `human_facing`：面向人类阅读的内容传 true，纯代码或数据传 false。标记为 true 的写入会进入审查，其余写入跳过。审查只看本次改动的区段。

批注暂存在 `~/.dsh/humanize/annotations/` 下。保存位置与被审查文件的路径一一对应。批注可以直接编辑。保存位置可以在设置页修改。

输入 `/humanize 路径` 合并指定文件或目录的批注。省略路径时使用当前工作目录。

批注合并在单独的上下文里进行。合并成功时，主会话会收到两行结果说明，分别报告合并完成和复审结果。合并完成后，暂存文件中的对应批注随之清空。插件再对刚改过的文件跑一次审查，这次审查称为复审，复审产生的新批注留在暂存里。

批注合并一开始，先中止正在运行的审查。排队中的审查直接丢弃，已经产出的批注也一并丢弃。

单次合并也会把待复审文件保存到文件里。合并或复审期间遇到插件重载，重载后的实例会补完这次复审，再结束合并。

输入 `/humanize-loop 路径` 循环执行批注合并与复审。每轮合并完批注后，对刚合并过的文件逐个复审。复审产生的新批注进入下一轮批注合并。直到复审没有新批注，或达到轮次上限为止。

合并运行的目标、轮次和待复审文件会保存到文件里。合并过程中遇到插件重载时，重载后的实例会接着往下跑。中途暂存的批注为空时，等复审跑完再判定是否收敛。

循环作为一个后台任务运行，进度条显示当前是第几轮，以及本轮有多少条批注。

可以在任务列表里取消，取消操作会在下一轮开始前生效。

在 profile 里配置了 hmr 监听本插件目录时，改动本插件自己的源码会触发插件重载。重载后，循环合并从上次停下的轮次接着跑。

输入 `/humanize-review 路径`，派发一次批次审查。审查范围是项目中受 git 管理的文件。

审查在后台进行，显示为一个后台任务。进度条在输入框上方更新。会话头部的任务列表同样显示该任务。审查在单独的上下文里进行，读到的内容与会话本身分开。

目标目录需要是 git 仓库，并且仓库状态能正常读取。任一条件缺失时，任务以失败结束并给出原因。

## 提示词

发给模型的提示词都放在包的根目录 `prompts/` 下，直接编辑即可：

- `prompts/review-system.md`：审查调用的 system 提示词，写入审查和批次审查共用。
- `prompts/merge-header.md`：合并消息开头的提示词，三种合并触发方式共用。
- `prompts/human-facing-field.md`：包装工具里 `human_facing` 字段的描述。

审查和合并每次调用都会重新读取对应的提示词文件。`human_facing` 字段的说明在注册包装工具时读取，改完后对新会话生效。
